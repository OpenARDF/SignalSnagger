# SignalSnagger 0.38.3 development release

This pre-1.0 development release promotes the hardware-tested 0.38.3l
candidate. It adds eyes-free gain feedback, selectable audio filtering, improved
battery reporting, and a configurable CW tuning offset while reducing audio
disruption from EEPROM persistence.

## User-visible changes

- Add `Push Beep`, `Turn Tick`, and `Gain Indic` controls to the SOUNDS menu so
  each sound can be enabled or disabled independently.
- Identify RF gain settings 0 through 10 with the approved audible cue patterns;
  the Morse-derived cues run at approximately 18 WPM, while gain 0 and gain 10
  retain their distinctive 300 ms long-pulse patterns.
- Suppress the startup beep when pushbutton beeps are disabled.
- Add OFF, 200 Hz, 400 Hz, and 800 Hz audio-filter choices. Encoder changes
  stop at the first and last choices instead of wrapping.
- Add a SETTINGS submenu and a CW offset setting of 0 or 500 through 1000 Hz in
  100 Hz steps, defaulting to 800 Hz. The displayed and stored frequency remains
  the carrier frequency while the Si5351 is tuned above it by the selected
  offset. Offset changes also stop at both endpoints instead of wrapping.
- In zero-offset mode, bypass the CW band-pass filter and tuning detector so the
  receiver can be zero-beat against a carrier.
- Improve the BATTERY display using calibrated voltage sampling and a bounded
  voltage-to-charge estimate.

## Stability, testing, and release workflow

- Move EEPROM byte updates into a bounded deferred queue so tuning and setting
  persistence do not stall the real-time audio path.
- Run the AVR test build with `-O2` while retaining debug symbols, giving the
  48 kHz capture and 12 kHz DSP paths representative execution headroom.
- Centralize audio decimation, gain, filtering, transition, DAC scaling, and
  analysis behavior in the tested `AudioPathProcessor`.
- Retune the three-bin Goertzel detector and audio-filter coefficients from the
  selected CW offset, while keeping the bins exactly 100 Hz apart.
- Append new settings to the EEPROM layout and normalize invalid or older stored
  values to safe defaults without disturbing existing memory data.
- Add host regression coverage for cue timing, sound settings, battery
  estimation, audio-filter response, non-wrapping controls, CW carrier-to-LO
  translation, zero-beat bypass, EEPROM defaults, and receiver retuning.

## Protected receiver behavior

The CW offset uses the existing carrier-frequency validation and
`si5351_set_quad_frequency` path. Displayed and EEPROM memory frequencies remain
operator-facing carrier frequencies. The experimentally established Si5351
quadrature implementation, divider and phase relationships, register values,
write order, and reset behavior are unchanged; only the requested oscillator
frequency is raised by the selected offset.

## Hardware qualification

Hardware evidence is inherited from the immediately preceding 0.38.3l
candidate under the documented pre-1.0 version-only promotion rule. On
2026-10-21, that exact candidate was programmed into an AVR128DA48 through
Atmel-ICE J41800053674 using an isolated flash erase. Programmer verification
passed; an independent 128 KiB readback matched the candidate byte-for-byte;
EEPROM, fuses, lock bits, and user row remained unchanged; and the target reset
at 3.29 V. The operator exercised the new CW offset and audio-filter controls,
reported the behavior acceptable, and observed maximum sensitivity with a
1000 Hz offset and the 800 Hz filter.

The only changed firmware input between 0.38.3l and this release is the
canonical `SW_REVISION` string. The exact 0.38.3 image was not programmed, so
exact-image boot/version confirmation was not performed. A structured repeat
of the startup/error and LED checks, exhaustive tuning/gain/audio/quadrature
and sensitivity checks, memory-frequency up/down checks, battery calibration,
all sound-cue combinations, headphone-removal 60-second countdown, power-down,
and headphone-reconnect startup was not performed. These omissions are
recorded as not performed, not as passed. The final artifact's embedded version
is verified statically during release preparation.
